# Контракт производительности Pure Camera

Core потребляет общий семантический контракт из `contract/`
и проецирует наблюдения на прозрачный HUD над нативным PreviewView. В web не передаются
кадры, пиксели, base64, RAW, видеопоток или большие дампы камеры. Работа с камерой,
кодеками, MediaStore и разрешениями выполняется в Kotlin.

## Инварианты, проверяемые автоматически

1. В JS ожидает не больше одного requestAnimationFrame. Между обновлениями нет
   recurring rAF, таймеров, polling или работы в фоне.
2. Входящие состояния используют mailbox ёмкостью одно последнее состояние.
   За один UI-кадр выполняется один commit, устаревшие состояния пропускаются.
   10 000 повторов уже отображённого состояния дают **ноль DOM-записей**.
3. Изменение таймера обновляет только его текст. DOM остаётся фиксированным,
   ссылки на элементы сохраняются при запуске, ARIA меняется вместе с UI.
4. Pinch вызывает мост не больше одного раза за UI-кадр. Множители событий
   перемножаются, последний не теряется после touchend. Пакет ограничен
   0.01–100; Kotlin проверяет диапазон и ограничивает масштаб возможностями камеры.
   touchcancel, потеря видимости, resize и отключение камеры сбрасывают жест.
5. Команды затвора передаются сразу. Ограничение частоты применяется к состоянию
   и непрерывным жестам, а не к нажатию кнопки.
6. В горячих обработчиках нет offsetWidth, getBoundingClientRect и других
   синхронных чтений layout. Фокус использует конечную Web Animation на
   transform/opacity; затвор анимирует только transform. Учтён reduced motion.
7. Скрытый документ отменяет ожидающий кадр, анимацию и жесты, сохраняет последнее
   состояние для возврата. Kotlin при onPause прекращает отправки.
8. Kotlin держит максимум один evaluateJavascript в полёте. Надёжные ответы и
   terminal capture events идут через ограниченную очередь; observations —
   через latest mailbox с deduplication. Callback прежнего WebView не освобождает
   слот нового renderer. Из-за snapshots фазы могут быть пропущены; terminal
   сообщения не теряются и не объединяются.
9. Только локальные ресурсы из budget manifest и системные шрифты. Без runtime-библиотек,
   внешних URL, canvas/video, фильтров и глобального will-change. Прозрачность
   html/body обязательна для нативного предпросмотра.

Бюджеты заданы в [performance-budget.json](../hud/performance-budget.json): всего 32 KiB
ресурсов, упаковываемых в APK; per-file лимиты заданы в manifest, DOM ≤64 элементов.
Это ограничения проекта, а не универсальные пороги браузера.

## Проверка

Из корня репозитория:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/web-check.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tools/run.ps1 test
```

Node 22 установлен только в `.pixi/envs/web-check`; тесты используют встроенные
`node:test`, `assert` и `vm`. esbuild 0.28.2 — локальный dev tool для минификации,
без runtime-зависимостей. Среда и кэши находятся внутри
проекта. Android `preBuild` автоматически запускает web-проверку, включая сборку
из Android Studio. Проверяется актуальность generated bindings, затем формируется
`hud/build/`, запускаются tests. В APK включается только этот каталог, тесты,
fixtures и replay не попадают. Одноразовые RPC deadlines ограничены 16 pending
командами и снимаются при settlement/dispose, в простое их нет.

Тесты проверяют нагрузку в 10 000 состояний, блокировку очередей, потерю
видимости, повторный renderer, накопление pinch, отсутствие layout reads,
таймеров и лишних DOM-записей. Эти проверки намеренно не зависят от скорости CI.
При добавлении поведения добавляй проверку соответствующего инварианта.

## Измерение на устройстве

Для изменения визуальных эффектов или мостового протокола запиши Chrome
Performance trace на целевом телефоне: idle 10 секунд, запись видео с таймером,
pinch, многократный фокус, поворот и фон/возврат. Ищи forced reflow, long tasks,
частоту bridge-вызовов, layout/paint и рост памяти. После idle не должно оставаться
повторяющихся задач интерфейса. Цель для JS commit — p95 до 2 мс на выбранном
телефоне; это цель измерения, а не гарантированный FPS.

Браузерный стенд с mock Native проверяет UI, но не заменяет замеры
Android WebView, camera preview, энергопотребления и композиции на телефоне.
Настоящий FPS зависит также от камеры, кодека, экрана и температуры устройства.

## Контрольный замер UI-слоя до выделения portable backend, 15 ноября 2026

Chrome DevTools, локальные файлы, viewport 390×844, mock Native:

| Сценарий | До | После |
| --- | --- | --- |
| 10 000 одинаковых состояний, DOM mutations | 100 000 | 0 |
| Подача этих состояний, CPU ×1 | 143,3 мс | 0,7 мс |
| DOM-элементы | 45 | 45 |

При CPU ×4 нагрузка в 12 000 состояний и 1 200 touchmove за 60 кадров дала 60 UI
commit и 60 native zoom-вызовов. p95 callback — 1,6 мс, максимум — 2,3 мс.
Cold-load trace: LCP 35 мс, CLS 0,00, три локальных ресурса, внешних запросов нет.
Эти лабораторные значения сохраняются как ориентир, не как порог CI или обещание
такой же скорости Android WebView. Основные регрессии блокируются
детерминированными тестами инвариантов.

Основания: [layout thrashing](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing),
[производительность анимаций](https://web.dev/articles/animations-and-performance).
